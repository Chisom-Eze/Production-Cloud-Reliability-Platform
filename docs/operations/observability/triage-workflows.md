# Stage J-B Observability Triage Workflows

## Standard Triage Sequence

1. DETECT: start from a CloudWatch alarm or Grafana observation.
2. SCOPE: identify the affected plane: edge, API, ECS, worker, queue, database, or AWS dependency.
3. CORRELATE: use `request_id`, `correlation_id`, or `trace_id` depending on the incident.
4. TRACE: use X-Ray when distributed execution path is relevant and a trace exists.
5. LOGS: use the Terraform-managed CloudWatch Logs Insights query definitions.
6. METRICS: use CloudWatch, AMP/PromQL, and Grafana to test hypotheses and determine blast radius.
7. MITIGATE: choose the least risky recovery mechanism, such as ECS rollback, restoring a known-good task revision, allowing queue retries, or scaling when saturation is confirmed.
8. VERIFY: confirm traffic health, task stability, queue recovery, stopped errors, normalized latency, and alarm recovery.
9. FOLLOW-UP: capture root cause, timeline, and corrective action.

## Metric To Log To Trace Examples

### API 5xx Or 502

CloudWatch alarm: `${project}-${environment}-api-5xx-error-rate-warning`

Then inspect `HTTPCode_Target_5XX_Count` and `HTTPCode_ELB_5XX_Count` separately. Use `${project}-${environment}/api/errors` to find Nginx/API error records. Use `request_id`, `correlation_id`, or `trace_id` to continue into `${project}-${environment}/correlation/request-lookup`, `${project}-${environment}/trace/trace-id-lookup`, and X-Ray.

If the 502 is generated by Nginx before FastAPI receives the request, FastAPI metrics and X-Ray traces may not exist for that request. That absence is diagnostic evidence that the failure boundary is before application execution.

### Worker Processing Failures

Start with `worker_jobs_processed_total{result="failure"}` or the `${project}-${environment}/worker/failures` query. Correlate `job_id` and `correlation_id` in logs. Then inspect `worker_job_claims_total`, `worker_outbox_dispatch_total`, `worker_visibility_heartbeat_failures_total`, SQS in-flight/visible messages, and database health.

### Queue Backlog Or Age

Start with `ApproximateAgeOfOldestMessage` and `ApproximateNumberOfMessagesVisible`. Compare worker `RunningTaskCount`, worker autoscaling status, worker failures, SQS in-flight messages, RDS health, and S3 artifact write evidence.

### DLQ Message

Start with the DLQ `ApproximateNumberOfMessagesVisible` alarm. Use worker failure logs and job context to determine whether processing, idempotency, SQS visibility, RDS, or S3 caused repeated failures. Do not purge or replay from the DLQ until root cause and replay safety are understood.

### Database Saturation

Start with RDS `CPUUtilization`, `DatabaseConnections`, `FreeStorageSpace`, and `FreeableMemory`. Correlate API `/ready` behavior, API database errors, worker processing failures, and latency. Use X-Ray for sampled app/database spans when available.

## PromQL Operating Queries

API request rate:

```promql
sum by (method, route, status_class) (rate(app_http_requests_total[5m]))
```

API server error rate:

```promql
sum(rate(app_http_requests_total{status_class="5xx"}[5m]))
/
sum(rate(app_http_requests_total[5m]))
```

API latency p50:

```promql
histogram_quantile(0.50, sum by (le, method, route) (rate(app_http_request_duration_seconds_bucket[5m])))
```

API latency p95:

```promql
histogram_quantile(0.95, sum by (le, method, route) (rate(app_http_request_duration_seconds_bucket[5m])))
```

API latency p99:

```promql
histogram_quantile(0.99, sum by (le, method, route) (rate(app_http_request_duration_seconds_bucket[5m])))
```

Worker job success/failure rate:

```promql
sum by (job_type, result) (rate(worker_jobs_processed_total[5m]))
```

Worker processing p95:

```promql
histogram_quantile(0.95, sum by (le, job_type, result) (rate(worker_job_processing_duration_seconds_bucket[5m])))
```

Outbox dispatch failure rate:

```promql
sum(rate(worker_outbox_dispatch_total{result="failure"}[5m]))
/
sum(rate(worker_outbox_dispatch_total{result="attempt"}[5m]))
```

Duplicate rate:

```promql
sum by (result) (rate(worker_duplicate_jobs_total[5m]))
```

Heartbeat failure rate:

```promql
sum by (operation) (rate(worker_visibility_heartbeat_failures_total[5m]))
```

## Dashboard Operating Model

Read the CloudWatch dashboard in this order:

1. EDGE: are users reaching healthy targets?
2. API/ECS: are application tasks healthy or saturated?
3. ASYNC QUEUE/WORKER: is async work arriving faster than it is processed?
4. DATABASE: is shared persistence the bottleneck?
5. AUTOSCALING: did capacity respond to demand?

## Grafana Operating Model

Grafana is the cross-signal visualization layer for CloudWatch, AMP, and X-Ray. Suggested future dashboard groupings are service overview, reliability/SLO, async pipeline, database, deployment/ECS, and incident correlation.

Do not duplicate every CloudWatch dashboard panel only because Grafana exists.

## Cardinality Guardrails

Forbidden metric labels:

- `job_id`
- `request_id`
- `correlation_id`
- `customer_id`
- UUID
- raw URL
- S3 object key
- exception message
- `trace_id`
- `span_id`

These belong in logs and traces. High cardinality causes memory pressure, higher AMP ingestion/storage cost, slower queries, and more operational complexity.

## Trace Sampling Guardrails

The code uses configurable parent-based trace ID ratio sampling with `OTEL_TRACES_SAMPLER=parentbased_traceidratio` and `OTEL_TRACES_SAMPLER_ARG`. Development currently defaults to `0.1`.

Do not hard-code 100 percent sampling. Higher sampling improves diagnostic fidelity but increases trace ingestion and storage cost. Lower sampling reduces cost but makes traces less complete. Parent-based sampling preserves distributed sampling consistency.

## Cost Drivers

Known cost drivers:

- CloudWatch log ingestion, storage, and Logs Insights queries
- enhanced Container Insights
- CloudWatch custom metrics, alarms, and dashboard usage
- AMP sample ingestion, storage, query volume, and cardinality
- X-Ray trace volume
- Amazon Managed Grafana workspace and active users
- ADOT sidecar CPU and memory on Fargate

CloudWatch Logs development retention is 7 days. AMP, X-Ray, and Amazon Managed Grafana retention behavior is not invented here.
